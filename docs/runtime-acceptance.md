最早一条事件在原 dot 未加载 QQ 工具时已经投递，随后超过被动回复期限。
该记录保留，没有补发或伪造入站。原私有插件按既有 App/Tunnel 绑定更新
后，新的本人消息才进入实际读取和回复流程；未核验的缓存机制不是已证明
根因。插件权限、服务身份及 App 连接未扩大。

服务重启本身通过了状态保持检查。原 dot 已只读核查后续两个未回复事件：
它们的合并触发附带了仅在 ChatGPT 确认、不回复来源应用的要求；该要求
不在保存的任务说明中，现有任务工具和页面未暴露其生成配置。只追加了
逐条处理全部 `message_id`、普通追问和限制说明也回原 QQ、区分任务确认
与答案送达的说明，保留同一任务、订阅、权限及飞书。新的连续两条回复
通过，但两条输入均没有那句附加要求，不能据此宣称平台合并批次机制已
修复，也不能把两个单事件格式当作两个独立执行 turn。

Webhook `2xx` 仅证明平台接收，
平台随后异步处理，并可按任务设置合并事件；见 [官方 MCP Events 文档](https://developers.openai.com/plugins/build/mcp-events#handle-delivery-responses)。
不能用投递成功代替最终回复，也不能自动重发未回复或结果不明的消息。
超过期限而未排队回答时，读取工具仍可返回 `reply.status=none`；诊断中
“过窗未回复”是由期限派生的状态，不等于数据库记录了 `expired` 回复。

真实验收使用普通本人私聊内容，无需代号。不能向其他成员发送测试，不能
伪造事件，也不能用机器人主动发送路径代替本人入站。后台 ACK 与本人
客户端可见结果分别记录；原生流式使用真正生成的递增文本。

QQ 当前仅本人 C2C 文本。群聊、频道、其他成员、入站附件和引用不在本次
运行范围；不能因为飞书支持这些能力就宣称 QQ 已支持。被动回复窗口、
uncertain 不重发、7 天逻辑保留和限流边界继续有效。

订阅最长 24 小时，由原 dot 平台按真实 `refreshBefore` 续订。桥不自行
延长 TTL，也没有新增 cron 或重复监测。到期后需要恢复或续订原任务，
保留唯一订阅、去重与 uncertain。一次成功收发不证明未来自然续订。

日志检查输出固定计数，不输出正文、凭据、身份或完整回调地址。业务 journal
最多 7 天、64M；全局 systemd 元数据按主机既有策略保留。数据库 7 天
逻辑清除不等于旧页、WAL、备份或系统日志的物理擦除。
